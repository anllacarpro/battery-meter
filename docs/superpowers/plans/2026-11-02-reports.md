# Battery Meter Reports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Reports pane with six reports (usage, discharge sessions, charging habits, health trend, sleep drain and top battery users), plus a "This week" card in Overview.

**Architecture:**
- All report logic lives in `BatteryCore` as pure functions over the history, parsed `pmset` events and stored app-energy samples. Each one has tests.
- The app adds two thin collectors: `PowerLogSource` runs `pmset`, and `EnergySampler` runs `top` every 5 min on battery.
- `ReportsModel` builds an immutable `BatteryReport` off the main thread, and the views only render it.

**Tech Stack:** Swift 6.4, SwiftPM, SwiftUI, Swift Charts, Foundation `Process`, Swift Testing.

**Spec:** `docs/superpowers/specs/2026-11-02-reports-design.md`. The first design, `docs/superpowers/specs/2026-11-01-battery-meter-design.md`, still applies.

**Branch:** `feat/reports`, cut from `feat/battery-meter`. PR 1 isn't merged yet, so the PR targets `feat/battery-meter`.

## Global Constraints

- Platform `.macOS("27.0")`, arm64, Command Line Tools only.
- Don't use SwiftUI `@State`, `@Entry` or `@Previewable`, because they don't build under Command Line Tools. Use `@Observable` objects or `@AppStorage` instead.
- Native look: system font, materials, system colors, light and dark mode. Use sentence case and no emoji.
- Never show values the data can't support. Every section has a "not enough data yet" state that names what it's waiting for.
- No report is built on the main thread.
- No admin rights. App names and sleep data never leave the Mac.
- The gap rule still applies: readings more than 300 s apart are not continuous. Builders sort input by timestamp first, because the clock can be set back.
- Fixed values:
  - **Usage:** the last 7 local days and the last 4 weeks, with weeks starting on `Calendar.current.firstWeekday`.
  - **Charging:** a 28-day window.
  - **Health trend:** needs at least 14 daily points spanning at least 14 days.
  - **Sleep:** the last 7 days, with periods of at least 30 minutes.
  - **Apps:** a sample every 300 s on battery, 30 days kept, the last 7 days shown, top 8.
  - **Refresh:** reports rebuild at most every 300 s. `pmset` is re-read at most every 1800 s.
- Stage files by explicit path only. The owner has untracked `.agents/`, `.claude/` and `skills-lock.json`.

## Review Focus

1. **Gaps aren't battery time.** A 2-hour gap between two on-battery readings (app quit or Mac asleep) must add nothing to battery time or charge used. Tested in Task 1.
2. **Out-of-order history.** After the clock is set back, the readings can be out of order. Reports must give the same result as for sorted input. Tested in Task 1.
3. **Garbled `pmset` lines.** A line with no `Charge:` or an unknown event is skipped. A sleep period that touches AC power is excluded rather than counted as drain. Tested in Task 4.
4. **`top` fails or prints nothing.** That gives no sample, no crash and no data written. Tested in Task 5.
5. **A tiny health slope.** A slope near zero must show "Health is steady", not an 80% date 400 years away. Tested in Task 3.

### Task 1: Usage report

**Files:**
- Create: `Sources/BatteryCore/UsageReport.swift`
- Test: `Tests/BatteryCoreTests/UsageReportTests.swift`

**Interfaces:**
- Consumes: `BatteryReading` (`timestamp`, `percent`, `externalConnected`, `powerWatts`).
- Produces:
```swift
public struct UsagePeriod: Equatable, Sendable {
  public var start: Date                 // local start of the day or week
  public var batteryTime: TimeInterval
  public var percentUsed: Int
  public var averageWatts: Double?       // nil when batteryTime == 0
}
public struct UsageReport: Equatable, Sendable {
  public var days: [UsagePeriod]          // exactly 7, oldest first, today last; zero-filled
  public var weeks: [UsagePeriod]         // exactly 4, oldest first, this week last
  public var hasData: Bool { get }        // any batteryTime > 0
  public static func build(history: [BatteryReading], now: Date, calendar: Calendar) -> UsageReport
}
```

Rules:
- Sort the readings, then walk consecutive pairs (a, b).
- A pair counts only if both readings are on battery and b.timestamp − a.timestamp ≤ 300 s.
- **Attribution:** the pair's duration goes to the period that contains a.timestamp.
- **Charge used:** the pair adds max(a.percent − b.percent, 0).
- **Average draw:** the mean of `powerWatts` over the a-readings of counted pairs.

  - `continuousDischargeToday`: 61 readings 60 s apart, on battery, dropping 1% every 6 readings, at 6 W. Today gives batteryTime 3600, percentUsed 10, averageWatts 6 (±0.01). The other days are 0.
  - `gapIsNotBatteryTime`: two readings 2 h apart, both on battery, 50% then 40%. Gives batteryTime 0, percentUsed 0 and `hasData == false`.
  - `acReadingsIgnored`.
  - `unsortedInputSameResult`: shuffled input equals the sorted result.
  - `sevenDaysAndFourWeeks`: `days.count == 7`, `weeks.count == 4`, and `days.last!.start == calendar.startOfDay(for: now)`.
- [ ] **Step 2:** Run `swift test --filter UsageReportTests` and expect a FAIL because the types are missing.

### Task 2: Charging habits report

**Files:**
- Create: `Sources/BatteryCore/ChargingReport.swift`
- Test: `Tests/BatteryCoreTests/ChargingReportTests.swift`

**Interfaces:**
- Produces:
```swift
public struct ChargingReport: Equatable, Sendable {
  public var chargeCount: Int              // AC runs in window
  public var typicalPlugInPercent: Int?    // median
  public var typicalUnplugPercent: Int?    // median
  public var averageDailyTimeAtFull: TimeInterval?  // over last 7 days, nil if no AC data in them
  public var cyclesPerWeek: Double?        // nil if window span < 7 days
  public var usualChargerWatts: Int?       // mode of adapterWatts on AC
  public static func build(history: [BatteryReading], now: Date) -> ChargingReport
}
```

Rules:
- **Window:** the last 28 days, sorted.
- **AC run:** a maximal run of readings with `externalConnected` where consecutive readings are ≤ 300 s apart.
- **Plug-in level:** the percent of the reading just before the run, if that reading is on battery and within 300 s. Otherwise it's the run's first percent.
- **Unplug level:** the run's last percent, but only if the next reading is on battery and within 300 s. Otherwise the run has no unplug level.
- **Time at full:** sum the pairs where both readings are on AC with percent ≥ 100 and are ≤ 300 s apart, over the last 7 days, then divide by 7.
- **Cycles per week:** (newest cycleCount − oldest cycleCount in the window) ÷ (span in days ÷ 7).

- [ ] **Step 1: Write the failing tests:**
  - `plugInAndUnplugMedians`: three AC runs plugged in at 20, 30 and 40 and unplugged at 80, 90 and 100. Expect plug-in 30, unplug 90 and chargeCount 3.
  - `timeAtFull`: 121 AC readings at 100%, 60 s apart, today (2 h). Expect averageDailyTimeAtFull 7200 ÷ 7 (±1).
  - `cyclesPerWeekNeedsAWeek`: a 3-day span gives nil. A 14-day span from 8 to 10 cycles gives 1.0.
  - `usualCharger`: the mode of 60, 60 and 30 is 60.
  - `emptyHistory`: every optional is nil and the count is 0.
- [ ] **Step 2:** Run `swift test --filter ChargingReportTests` and expect a FAIL.

### Task 3: Health trend and shared daily health

**Files:**
- Create: `Sources/BatteryCore/DailyHealth.swift`, `Sources/BatteryCore/HealthTrend.swift`
- Modify: `Sources/BatteryMeter/HistoryView.swift`. Its private `dailyHealth` and `HealthPoint` move to BatteryCore, and `HistoryData` calls `DailyHealth.points(in:)`.
- Test: `Tests/BatteryCoreTests/HealthTrendTests.swift`

**Interfaces:**
- Produces:
```swift
public struct HealthPoint: Identifiable, Equatable, Sendable { public let day: Date; public let percent: Double; public var id: Date { day } }
public enum DailyHealth { public static func points(in history: [BatteryReading]) -> [HealthPoint] }  // same algorithm as today's HistoryView.dailyHealth
public enum HealthTrend: Equatable, Sendable {
  case notEnoughData(daysCollected: Int)
  case steady(currentPercent: Double)
  case declining(currentPercent: Double, lossPerMonth: Double, reaches80: Date?)  // nil if > 10 years out
  public static func build(points: [HealthPoint]) -> HealthTrend
}
```

Rules:
- It needs at least 14 points spanning at least 14 days. Otherwise it returns `.notEnoughData` with the point count.
- Fit a least-squares slope in percent per day.
- A slope ≥ −0.001 gives `.steady`.
- `lossPerMonth` = −slope × 30.
- `reaches80` = the last day + (current − 80) ÷ −slope days. It's nil if current ≤ 80 or the result is more than 10 years out.
- `currentPercent` is the fitted value on the last day.

- [ ] **Step 1: Write the failing tests:**
  - `tooFewDays`: 10 points gives `.notEnoughData(daysCollected: 10)`.
  - `flatIsSteady`: 30 points at 98.8 gives `.steady`.
  - `tinySlopeIsSteady`: −0.0005 per day gives `.steady`. This is Review Focus 5.
  - `decliningProjects80`: 30 days falling linearly from 100 to 97 gives lossPerMonth ≈ 3.10 (±0.05), and reaches80 is about 164 days after the last point (±2 days).
  - `dailyHealthMovedUnchanged`: the existing behaviour, with 2 days of readings giving 2 points at local noon.
- [ ] **Step 2:** Run `swift test --filter HealthTrendTests` and expect a FAIL.
- [ ] **Step 3:** Implement the two files. Switch `HistoryView` to `DailyHealth.points(in:)` and delete the moved code.

### Task 4: Sleep log parser and sleep drain report

**Files:**
- Create: `Sources/BatteryCore/SleepLog.swift`, `Sources/BatteryCore/SleepReport.swift`
- Test: `Tests/BatteryCoreTests/SleepReportTests.swift`

**Interfaces:**
- Produces:
```swift
public struct PowerEvent: Equatable, Sendable {
  public enum Kind: Sendable { case sleep, wake, darkWake }
  public var date: Date; public var kind: Kind; public var onBattery: Bool; public var charge: Int; public var reason: WakeReason?
}
public enum WakeReason: String, CaseIterable, Sendable { case lid, userInput, network, scheduled, powerButton, other }
public enum SleepLog { public static func parse(_ text: String) -> [PowerEvent] }
public struct SleepPeriod: Equatable, Sendable { public var start: Date; public var end: Date; public var percentLost: Int; public var darkWakes: Int }
public struct WakeReasonCount: Equatable, Sendable { public var reason: WakeReason; public var count: Int }
public struct SleepReport: Equatable, Sendable {
  public var periods: [SleepPeriod]                 // newest first
  public var percentPerHour: Double?                // total lost / total hours
  public var wakeReasons: [WakeReasonCount]        // descending by count
  public static func build(events: [PowerEvent], now: Date) -> SleepReport
}
```

Parsing rules:
- **Event lines:** a line is an event only if it matches `^(\d{4}-\d\d-\d\d \d\d:\d\d:\d\d [+-]\d{4}) (Sleep|Wake|DarkWake)\s` followed by a tab. That excludes lines such as "Wake Requests".
- **Power source and charge:** read `Using (Batt|BATT|AC) \(Charge:(\d+)%\)`, ignoring case. Skip the line if this is missing.
- **Reason:** the text between `due to ` and ` Using`, for `wake` and `darkWake` only. Categories are checked in this order, ignoring case:
  - "lid" as a whole word (`\blid\b`) → `lid`
  - "power button" or "pwrbtn" → `powerButton`
  - "HID" or "multi-touch" or "keyboard" → `userInput`
  - "wifi" or "ARPT" or "network" or "en0" → `network`
  - "rtc" or "maintenance" or "scheduled" → `scheduled`
  - anything else → `other`

Report rules:
- **Sleep period:** runs from a `sleep` event to the next `wake`. Any `darkWake` events in between count toward `darkWakes`.
- **Kept periods:** keep a period only if every event in it has `onBattery`, it lasted at least 1800 s, and it ended in the last 7 days.
- **Loss:** `percentLost` = max(first sleep charge − wake charge, 0).
- **Wake reasons:** count every `wake` and `darkWake` in the 7 days.

Use these fixture lines, copied from the owner's Mac, in a test resource string:
```

2026-11-01 21:10:32 -0500 Wake Requests       	[process=dasd request=SleepService deltaSecs=952]
2026-11-01 21:15:38 -0500 DarkWake            	DarkWake from Deep Idle [CDNP] : due to smc.sysState.Wake(0x70070000) wifibt SMC.OutboxNotEmpty centauri-alpha E_TKO_NO_RESPONSE ARPT/ Using BATT (Charge:50%) 5 secs
```

### Task 5: Top battery users (parser, store and report)

**Files:**
- Create: `Sources/BatteryCore/TopEnergyParser.swift`, `Sources/BatteryCore/AppEnergyStore.swift`, `Sources/BatteryCore/AppEnergyReport.swift`
- Test: `Tests/BatteryCoreTests/AppEnergyTests.swift`

**Interfaces:**
- Produces:
```swift
public struct ProcessPower: Equatable, Sendable { public var pid: Int32; public var command: String; public var power: Double }
public enum TopEnergyParser { public static func parse(_ output: String) -> [ProcessPower] }  // second sample only
public struct AppEnergyStore: Sendable {          // file: [dayKey "yyyy-MM-dd": [appName: impactSeconds]]
  public init(fileURL: URL)
  public static var defaultURL: URL               // ~/Library/Application Support/BatteryMeter/app-energy.json
  public func add(_ impacts: [String: Double], on day: String) throws   // merge-add, prune days older than 30, atomic write
  public func load() -> [String: [String: Double]]  // never throws; missing/corrupt -> [:]
  public func reset() throws
}
public struct AppShare: Equatable, Sendable { public var name: String; public var share: Double }  // 0...1
public enum AppEnergyReport { public static func build(days: [String: [String: Double]], now: Date, calendar: Calendar) -> [AppShare] }  // last 7 days, top 8, desc
```

Parser rules:
- Find the second line that starts with `PID`. Parse the rows below it until the first blank line.
- **Row format:** the pid is the leading integer and power is the last number. The command is everything between them, trimmed.
- **Skipped rows:** `command == "top"` and `power <= 0`.
- No second header (for example empty output, or `top` failing) gives `[]`.

Store rules:
- **Day key:** local `yyyy-MM-dd` via a POSIX formatter.
- **Pruning:** `add` drops keys older than 30 days relative to the day being added.
- **Writes:** use `Data.write(options: .atomic)`, guarded by a serial queue, the same pattern as `HistoryStore`.

Report rules:
- Sum each app over the last 7 day keys.
- `share` is the app's total ÷ the grand total. Take the top 8.

  ```
  88845  Claude Helper (R 11.7
  90630  top              6.3
  35686  WhatsApp         7.7
  ```

**Interfaces:**
- Produces:
```swift
public struct BatteryReport: Equatable, Sendable {
  public var generated: Date
  public var usage: UsageReport
  public var sessions: [DischargeSession]          // newest first
  public var charging: ChargingReport
  public var health: HealthTrend
  public var sleep: SleepReport
  public var apps: [AppShare]
  public static func build(history: [BatteryReading], powerEvents: [PowerEvent],
                           appEnergy: [String: [String: Double]], now: Date, calendar: Calendar) -> BatteryReport
}
@MainActor @Observable final class ReportsModel {
  var report: BatteryReport?
  init(battery: BatteryModel, energyStore: AppEnergyStore, logSource: PowerLogSource)
  func refresh(force: Bool = false)   // no-op if last build < 300 s ago and !force; builds in Task.detached(priority: .utility)
}
struct PowerLogSource: Sendable { func read() async -> String? }   // runs /usr/bin/pmset -g log; nil on failure; caller caches 1800 s
@MainActor final class EnergySampler {
  init(battery: BatteryModel, store: AppEnergyStore)
  func start()   // Timer every 300 s; skips unless battery.reading?.externalConnected == false; runs top off-main; names via NSRunningApplication(processIdentifier:)?.localizedName ?? command; impactSeconds = power * 300
}
```

Decisions:
- Both `Process` runs use absolute executable paths and a 10 s timeout. They read stdout to end, and their errors are swallowed into `nil` or `[]`.
- The `pmset` text is cached in `ReportsModel` with its timestamp.
- The `BatteryReport.build` test checks that the composition is wired correctly. Build it from small fixtures and assert that each sub-report equals its own builder's output.
- `ReportsModel` uses a generation counter, like `BatteryModel`, so a slow build can't overwrite a newer one.
